## Project Overview

**TYP** is a Ghana-focused exam-prep and digital skills platform. BECE (Junior High School exit exam) is the flagship track currently built out in the UI, but the platform is scoped to cover multiple exam/skill tracks: **BECE, WASSCE, nursing entrance/licensing exams, university entrance exams, and digital skills training.** Schools subscribe to give their students access to practice assessments; individual ("independent") students can also self-subscribe. Content is produced by content admins, vetted by a super admin, then made available as timed assessments students take online with automatic scoring, results, progress tracking, and leaderboards.

**Decided 2026-08-05 — the product is growing into two deliberately separate systems, not one:**
1. **The exam-prep track** (everything described above and already built in the UI) — internal Content Admins, super-admin pre-approval, `Program`/`Subject`/`Question`/`Assessment`/`ExamAttempt`. **Stays exactly as-is, untouched by the below.**
2. **A new course marketplace**, Coursera/Udemy-style — independent **Tutors** self-onboard and publish real courses (video lessons, reading material, structured modules — not just timed assessments) directly to students. Key decisions locked in:
   - **Moderation**: publish-first, moderate-after (not pre-approved like the exam-prep track) — matches real marketplace scale, not the internal vetted-content trust model.
   - **Payment**: a la carte per course — a tutor sets a price, the platform takes a cut (split payment), rather than a pooled subscription revenue-share.
   - **Enrollment**: per-course (`Course → Enrollment → Student`), no fixed tutor roster — a student can enroll in courses from many different tutors independently.
   - **Content Admin and Tutor are two distinct roles, not a merge** — different onboarding (internal/vetted vs. self-service), different trust level, different content pipeline.
   These two systems will likely share only `User` (base identity/auth) and `Student` identity — `Course` is not an `Assessment`, and the marketplace's trust/payment model is intentionally not the exam-prep track's. **The entity design is now decided and in `prisma/schema.prisma`** (`TutorProfile`, `Course`, `Module`, `Lesson`, `Enrollment`, `CoursePurchase` — see the dedicated `Decided/built` entry below for the full design pass and rationale). **No UI/Server Actions exist yet for any of it** — this was explicitly a schema-only design pass, per this section's own "needs its own design pass... before implementation starts" rule.

**Decided 2026-08-05**: "exam program/track" is modeled as a dedicated top-level `Program` entity (BECE, WASSCE, Nursing, University Entrance, Digital Skills). `Subject.programId` is a FK to it — each subject belongs to exactly one program (a subject like Biology that feeds both WASSCE and Nursing becomes two separate `Subject` rows, since content/difficulty/topics differ by program anyway). `Assessment`/`Question`/`StudyMaterial` inherit their program transitively through `Subject`. See [`docs/data-model.md`](./docs/data-model.md#the-central-open-gap-exam-program--track) for full rationale.

**Decided/built 2026-08-05 — `super-admin/review-queue` is now real, closing the loop opened by `content-admin/questions`'s "Submit for Review" and proving Assessment has a real schema gap Question doesn't**:
- **`Assessment` has no `rejectionReason`/`reviewedBy` columns** (unlike `Question`, which has both) — see `docs/data-model.md`. Rather than adding columns to a schema owned by a concurrent session, the review history for *both* Question and Assessment now reads from `AuditLog` (`action: "approve"|"reject"` already existed as valid enum values, seemingly anticipating exactly this) — `AuditLog.details` (JSONB) carries `{ type: "question"|"assessment", ...ids, reason? }`. This is arguably more correct than the Question-only columns anyway: it's one unified, queryable review trail instead of state bolted onto two different content tables. **When picking this up for real**: consider whether `Question.reviewedById`/`rejectionReason` should also move to AuditLog-only for consistency, or whether AuditLog should be treated as the source of truth for "was this ever rejected and why" while the content table's own fields stay as a fast-path cache of the *latest* review only.
- **Root-caused a genuine Neon free-tier concurrency limit**: this page's initial `Promise.all` of 9 queries reproduced a `{clientVersion: "7.9.1"}` Prisma error intermittently (~50% of requests) *inside the Next.js dev server specifically* — the identical 9-query batch succeeded 100% of the time as a standalone `tsx` script. - **THE NEON OUTAGE: root-caused and fixed, not just retried past.** This dev sandbox has no real IPv6 route. Node's default connection behavior (`net`'s Happy Eyeballs / `internalConnectMultiple`) races *every* resolved address — IPv4 and IPv6 — concurrently. The IPv6 attempts fail instantly (`ENETUNREACH`), and that burst was observed to make the *IPv4* attempts fail too (`ETIMEDOUT`, ~50% of the time), even though a single isolated IPv4 connection to the exact same host always succeeded instantly in isolation. **Fix, now in both `lib/prisma.ts` and `prisma/seed.ts`**: `net.setDefaultAutoSelectFamily(false)` + `dns.setDefaultResultOrder("ipv4first")`, called before any Prisma/Neon code runs. Verified 5/5 consecutive successful queries after the fix, vs. frequent failures before. **This was a real, fixable bug in this environment, not an external Neon incident** — don't waste time checking Neon's status page if this class of error recurs; check this fix is actually in place first.

**Decided/built 2026-08-05 — Auth.js is wired up for the exam-prep track's 4 roles** (`super_admin | content_admin | school_admin | student`; the Tutor role is not part of this, see the marketplace section above):
- **No `@auth/prisma-adapter`** — deliberately, per the "own Postgres users table" decision. Credentials provider + JWT session strategy needs no adapter at all (no `Account`/`Session`/`VerificationToken` tables), so `prisma/schema.prisma` didn't need touching.
- **Config is split into two files**: `auth.config.ts` (edge-safe: no Prisma/bcrypt imports, just callbacks + pages config) and `auth.ts` (full config: adds the `Credentials` provider, which does need Prisma to look up the user and bcrypt to compare the password hash). `proxy.ts` builds its own lightweight `NextAuth(authConfig)` instance from the edge-safe config only — it must never import `auth.ts` directly, or Prisma/bcrypt get bundled into every single request's proxy invocation.
- **`middleware.ts` is `proxy.ts` in this Next.js version** (Next 16 deprecated and renamed the file convention — confirmed via the bundled `node_modules/next/dist/docs`, not assumed). `proxy.ts` at the repo root does the role-based route protection: unauthenticated → redirect to `/login?callbackUrl=...`; authenticated but wrong role for the path prefix → redirect to that role's own dashboard root (never a 403/loop).
- **Server Components calling `auth()` cannot pass the results straight into a Client Component if other props (like a nav array containing lucide icon components) are mixed in** — functions/components aren't serializable across the RSC boundary. Fixed by splitting each of the 4 role layouts into a thin Server Component (`layout.tsx`, calls `auth()`, passes only plain strings) wrapping a small Client Component (`*-shell.tsx`, owns the icon-laden navigation array locally). Follow this pattern for any future layout that needs both session data and an icon-based nav.
- **Neon's serverless driver needs `neonConfig.webSocketConstructor = ws`** on this project's Node 20 (no native `WebSocket` global below Node 22) — same fix as the seed script, now centralized in `lib/prisma.ts` (a singleton, cached on `globalThis` in dev to survive HMR without exhausting the connection pool). Always import `prisma` from there, never instantiate `PrismaClient` directly elsewhere.
- Verified end-to-end against the live seeded Neon DB: login (correct + wrong password), session contents, dashboard rendering real seeded user data, cross-role redirect (student → `/super-admin` bounces back to `/student`), and sign-out (via `dashboard-shell.tsx`'s "Sign out" now calling real `signOut()`, previously just a dead `<Link href="/login">`).

**Decided/built 2026-08-07 — `content-admin/questions/upload` (bulk CSV/XLSX) is wired; first genuinely new subsystem in the Content Admin lane, not just a page rewire**:

## Key Workflows

1. **School onboarding** (`app/signup/school`) — 5-step wizard (school info → location → administrator account → school size → plan) ending in `pending` verification status, not immediate activation. A super admin (or automated check) must verify before the school is `active`.
2. **Student onboarding** — either provisioned by a school admin (`app/school-admin/students/add`, no billing) or self-service independent signup (`app/signup/independent`, 4 steps including mandatory guardian contact info and an explicit guardian-approval acknowledgment before checkout).
3. **Content pipeline** — content admin creates/uploads questions → `pending` → super admin reviews in the Review Queue (`app/super-admin/review-queue`) → `approved` (enters the question bank, usable in assessments) or `rejected` (with a reason, content admin can revise & resubmit). Same pattern applies to assessments.
4. **Bulk upload** — CSV/XLSX with required columns (`question, option_a..d, correct_answer`) and optional (`subject, topic, difficulty, explanation`); client-side preview shows per-row valid/warning/error status before committing. Needs a real parser + validation service server-side (the demo data is hardcoded).
5. **Assessment taking** (`app/student/exams/[id]/start`) — timed, question-by-question with a navigator grid (answered/current/flagged states), auto-submits on timeout, confirms before manual submit. Needs a real anti-cheat/session story eventually (tab-switch detection, one-attempt enforcement) — not yet decided, flag if asked to build this.
6. **Billing** — school admins see plan/usage/invoices/payment method (`app/school-admin/subscription/**`); super admin sees platform-wide revenue and payments (`app/super-admin/revenue`, `/payments`). All amounts are GHS.

## Tech Stack

**Frontend**
- Next.js (App Router) + TypeScript + Tailwind CSS v4, shadcn/ui (Radix primitives) — already built, keep conventions consistent with existing pages
- Deployed on Vercel (this repo is v0-linked; merges to `main` auto-deploy)

**Backend** — *decided: Next.js fullstack, not a separate service*
- Server actions / API routes inside this same Next.js app — no separate NestJS service. Chosen for speed of shipping and to keep one codebase/one deploy on Vercel, since the team needs to get a working backend live, not stand up new infra.
- Zod for validation (already a dependency, already used with react-hook-form on the client — reuse the same schemas server-side)

**Database**
- PostgreSQL via **Neon** (serverless, branches per Vercel preview deployment)
- Prisma as ORM

**Auth** — *decided: Auth.js + own Postgres users table*
- Full control needed for the 4-role model, school-level multi-tenancy (a school admin's queries must scope to their school), and the guardian-approval flow on independent student signup — none of which a stock managed-auth product handles out of the box.

**Payments** — *decided: Paystack*
- Matches the Ghana-market focus (GHS pricing, mobile money support is essential here, not optional). Route all payment logic through an internal interface/service layer rather than calling the Paystack SDK directly from business logic, so a second processor could be added later without a rewrite — but don't build that abstraction speculatively beyond a thin interface until there's an actual second processor to support.

**File storage**
- **Vercel Blob** for CSV/XLSX bulk-upload files and any question images/diagrams — stays native to the stack already in use, no extra vendor account needed at current scale.

**Background jobs**
- Not yet decided. Bulk upload processing and CSV validation currently run client-side in the demo; a real implementation likely needs either a queued job (for large files) or can stay synchronous in an API route if files stay small (≤5MB per the current UI copy). Flag this as a decision point if bulk upload volume becomes a real concern.

## Architectural Principles

1. **The frontend is the source of truth for product behavior.** Don't redesign flows, statuses, or role permissions while building the backend — match what's already built in `app/**`. If something seems wrong or incomplete, raise it as a question rather than silently changing it.
2. **No vendor lock-in beyond what's been deliberately decided.** Neon/Prisma/Auth.js/Paystack/Vercel Blob are the agreed stack — don't introduce additional SaaS dependencies without flagging it first.
3. **Payment logic goes through an internal interface**, never called directly from route handlers/business logic — see Payments above.
4. **Role/tenancy scoping is a hard requirement, not an afterthought.** Every school-admin and student query must be scoped to their school (or to "no school" for independent students) at the data-access layer, not just hidden in the UI.
5. **Approval workflows are core, not incidental.** Questions and assessments are never directly published by a content admin — the `pending → approved/rejected` gate is a first-class part of the data model and must be enforced server-side, not just presented as a UI state.

**Decided/built 2026-08-08 — a full security/consistency audit found and fixed a real, exploitable `passwordHash` leak across 14 pages, plus 2 real defense-in-depth gaps. This is the most severe finding this whole project has had - documented in full rather than just "fixed and moved on."**

A read-only background agent was tasked with auditing three things across the entire app: (1) missing/wrong auth guards on Server Actions, (2) tenant-scoping gaps, (3) `User.passwordHash` leaking across the RSC boundary. Methodology: enumerated all 43 `"use server"` files, every dynamic `[id]` Server Component route, and every Prisma query anywhere in `app/` that includes a `user`/`createdBy`/`reviewedBy`/`actor` relation, then read each one rather than sampling.

**Category 3 (passwordHash leak) - CRITICAL, real and exploitable.** 14 pages (12 found by the audit, 2 more found by a follow-up manual sweep of every remaining `include: { user: true }`-style query in the app) fetched a full `User` row via `include: { user: true }` (or `createdBy: true`/`reviewedBy: true`/`actor: true`) and passed it - unmapped, or only shallow-spread (`{...row}`) - straight into a `"use client"` component's props. Since RSC props are serialized into the page's initial HTML/flight payload, this meant any authenticated super admin (and, for two pages, any school admin) loading an existing page received other real users' actual bcrypt `passwordHash` values, visible via View Source with no devtools tricks needed. This is exactly the mistake `school-admin/settings` caught and fixed in itself back on 2026-08-07 ("strip passwordHash has to happen per-row on any list of User-including records, not just the one the page happens to be about") - that lesson evidently didn't propagate to every other page built afterward, since individual sessions verified their own pages in isolation and this is the first pass to check the *whole app* at once.

Fixed sites, by pattern:
- **Destructure-after-fetch** (`const { passwordHash: _x, ...safeUser } = user`, matching the already-correct pattern from settings pages): `super-admin/courses/[id]/page.tsx` (tutor + every enrolled student), `super-admin/schools/[id]/page.tsx` (every admin, `primaryAdmin` re-derived from the now-safe list), `super-admin/tutors/[id]/page.tsx`, `school-admin/students/page.tsx` (every student in the school), `school-admin/assessments/assign/page.tsx` (every student in the picker), `super-admin/tutors/page.tsx`, `super-admin/content-admins/page.tsx`, `super-admin/courses/page.tsx`.
- **Query-level `select` instead of `include: true`** (the stronger fix - Prisma never fetches the column from Postgres at all, not just strips it after the fact): `super-admin/payments/page.tsx` (`invoice.subscription.student.user`, the deepest-nested case), `content-admin/assessments/page.tsx` (`createdBy`), `super-admin/question-bank/page.tsx` (`createdBy` **and** `reviewedBy` - two different users per question), `content-admin/questions/pending/page.tsx` (`reviewedBy`), `super-admin/page.tsx` + `super-admin/audit-logs/page.tsx` (`actor`, nullable).
- **Found and fixed one more not in the audit's original list**: `super-admin/revenue/page.tsx` shares the exact same `invoice.subscription.student.user` pattern as `payments` - re-checked it specifically for that reason. It turned out **not** to be an actual leak (its `recentTransactions` already only derives a plain `payerName` string, never passes the raw user object down) but was tightened to `select` anyway for consistency and to stop fetching `passwordHash` from the DB at all even though it was never serialized.
- **Every client component's own prop type also had to be corrected**, not just the query - each one had declared its prop as the full `User`/`Student & { user: User }` shape, which is what caused a cascade of `tsc` errors once the queries were narrowed (a real, useful signal: TypeScript correctly caught the query/type mismatch in 9 of the 14 files). Fixed by changing each type to `Omit<User, "passwordHash">` (when all other User fields are still genuinely needed) or a minimal `{ id: string; name: string }`-style shape (when only `.name` is ever rendered, matching what was actually `select`ed). **One file's type didn't error despite being wrong** (`super-admin/payments/payments-view.tsx`'s `SubscriptionOwner.student.user: User`) - fixed for correctness anyway even though `tsc` didn't force it; the runtime fix (the query-level `select`) was already fully effective regardless, since Prisma enforces `select` at the database level independent of how the TypeScript type on the receiving end is declared.

**Category 1 (auth guards) - two real, fixed gaps, plus one documented-not-fixed systemic pattern.**
- **`initializeSchoolCheckout`/`initializeStudentCheckout`** (`app/signup/school/actions.ts`, `app/signup/independent/actions.ts`) never verified the caller owns the `schoolId`/`studentId` they passed - exploitable to create arbitrary pending `Payment` rows and probe school/student existence via differing error messages (not directly exploitable for financial fraud, since the webhook remains the sole source of truth for whether a charge succeeded and amounts are computed server-side from the real plan/course price - a defense-in-depth gap, not a payment-forging one). Both are genuinely called two ways: `initializeStudentCheckout` only ever runs *after* a real sign-in (the independent-signup wizard calls `signIn()` before checkout, with an early return if it fails), so it now unconditionally requires a session matching `student.userId`. `initializeSchoolCheckout` is trickier - it's also called anonymously, moments after `registerSchool`, since school-admin signup deliberately does *not* auto-sign-in (a pending-review flow). This is a real deviation from this project's own stated defense-in-depth principle (NFR-SEC-1) and is the reason the three dynamic-`[id]` pages above had no independent verification the viewer is even a real super admin - but it's currently unexploitable (`proxy.ts` genuinely blocks the wrong role from the whole `/super-admin/*` prefix before any page code runs), and retrofitting an explicit `auth()` check onto ~15 already-shipped pages for redundant protection is a disproportionate amount of churn for a currently-non-exploitable gap relative to the two real fixes above. Flagged here as a real, known finding for a future dedicated pass, not swept under the rug.
- **Every other Server Action across the app was confirmed in good shape**: role/tenant resolved server-side from the session (never a client-supplied id) before trusting anything else, with ownership consistently re-verified on mutations (`deleteQuestion`/`updateQuestion` re-check `createdById`, `submitExam`/`recordTabSwitch` re-check `attempt.studentId`, etc.).

**Category 2 (tenant-scoping) - zero issues found, a genuine clean result, not an unchecked category.** Every school-admin/student query that resolves an id is scoped server-side from a `SchoolAdmin`/`Student` record resolved from the session; every dynamic-`[id]` route independently re-verifies ownership rather than trusting that a link only appeared because a list page filtered it correctly (several with an explicit comment saying exactly that). There are no school-admin dynamic-`[id]` routes at all - school-admin pages only ever operate on the caller's own resolved `schoolId`.

**Decided/built 2026-08-08 — an N+1/expensive-query audit found and fixed one real N+1 pattern (present in 2 pages) plus one genuinely missing index it directly benefits from**:
- **Methodology**: grepped every `page.tsx`/`actions.ts` for `.map(async`, `for (...)` loops, and any file with multiple `await prisma.` calls, then read each candidate directly rather than pattern-matching alone (most hits turned out to be pure in-memory aggregation over an already-fully-fetched array - not a query per iteration, just a `for` loop doing arithmetic - which is fine and was left alone). - **The real N+1, found in two near-identical files**: `student/results/page.tsx` and `student/page.tsx` (a duplicated-on-purpose `getRank` helper, per this project's own "two routes independently deployable" precedent for this exact pair) both called a per-attempt `getRank(assessmentId, attemptId)` function **inside a loop over the student's own submitted attempts** - one full `examAttempt.findMany` round trip per attempt, not per page load. `student/results/page.tsx`'s loop was uncapped (every submitted attempt a student has ever made); `student/page.tsx`'s was capped at 3 ("Recent Results"), a smaller but structurally identical instance.
